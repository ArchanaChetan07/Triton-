Executive summary

This document is the full story of one focused piece of work: turning a career question — "what are my chances at OpenAI?" — into a concrete, verified fix for a real bug in Triton, the GPU compiler that OpenAI created and still maintains.

The arc has six movements. We start with a résumé and an honest assessment. We identify the true bottleneck — a lack of verifiable public work — and pick a bug that puts that work directly in front of the people who would hire her. We reproduce the bug, dig down through the compiler until we find the exact mechanism, write a fix, and then — critically — turn the same skeptical eye on our own fix and find and repair the bugs hiding in that.

The result in one line A chained floating-point division feeding a reduction made Triton emit 4,128 hardware divide instructions where ~64 were needed. The cause is a single layout decision in one compiler pass. The fix is a ~20-line, principled change with a regression test — sitting on a branch, as a clean patch, ready to build and open as a pull request.

Part I — The big picture Beginner

1. It started with a résumé

The project began with a simple ask: "Here's my résumé — what are my chances of getting into OpenAI?" The résumé was strong and unusually well-targeted at LLM-inference infrastructure: CUDA and Triton kernels, KV-cache quantization, speculative decoding, tensor parallelism. But an honest assessment surfaced three hard truths that no amount of polish could hide:

  • Under a year of full-time engineering experience.
  • No brand-name employer to act as a credential shortcut.
  • Open-source contributions that were "open, under review" — not merged, not yet proof.

OpenAI is one of the hardest places in the industry to be hired. A cold résumé with those three gaps is usually filtered out before a human reads the good parts.

2. The real bottleneck

Beginner note — what a "bottleneck" is here Years-of-experience and a famous employer are just proxies a reviewer uses to answer one question: "can this person do elite work?" If you cannot offer the proxies, the only way through is to make them irrelevant — with public, verifiable, hard work in the exact domain the employer cares about.

So the bottleneck was reframed. Not "get more experience" (slow, uncontrollable) but: produce undeniable public evidence of skill, where OpenAI engineers will see it. The sharpest possible venue for that is Triton itself.

3. What is Triton, and why it matters

Beginner note — the vocabulary A GPU runs thousands of tiny threads in parallel. A kernel is one small program those threads run. Writing fast kernels in raw CUDA is hard, so Triton is a language + compiler that lets you write kernels in Python-like code and compiles them to GPU machine code. Triton was created at OpenAI and is still led by OpenAI engineers. vLLM is a popular library that serves large language models fast, and leans on kernels like these.

Because Triton is OpenAI's own project, a genuinely useful, merged fix to Triton is about the most direct signal a candidate can send. It lands in the commit history that OpenAI engineers read and review. That is why, of all the possible open-source targets, Triton was the bullseye.

4. Choosing bug #10987

Scanning Triton's open issues for something meaty but tractable surfaced #10987, titled — almost unbelievably — "Triton generates pathologically large PTX for chained fp32 division-by-broadcast feeding a reduction." In plain terms: a trivial kernel was compiling into eleven thousand lines of low-level code and taking thirteen seconds to assemble. Something was very wrong, the report was crisp, and nobody had claimed it.

Why this bug was the right pick It lives in Triton (maximum signal), it is a real correctness-adjacent performance bug (not a typo fix), it was precisely reported with a reproducer, and — as we will see — it turned out to be verifiable without owning an expensive GPU, which matched the constraints exactly.

Part II — Reproducing the bug Intermediate

5. The toolchain and the real-world hurdles

Before you can fix a bug you must make it happen on your own machine, on demand. This is where real engineering — as opposed to the tidy version in tutorials — actually lives. The environment was a Windows 11 laptop with a small NVIDIA T1000 GPU. The road there had three genuine potholes, each worth remembering:

Hurdle 1 — Triton would not even import on Windows Installing Triton for Windows produced ImportError: DLL load failed while importing libtriton: A dynamic link library (DLL) initialization routine failed. This happened on two different versions — the tell-tale sign of an environment-level incompatibility between Triton's bundled LLVM and the installed PyTorch, not a version mismatch that swapping would fix.
Hurdle 2 — the shell kept mangling commands Commands sent from PowerShell into WSL kept dying after the first line. The cause was subtle: PowerShell was intercepting $(...) command-substitution and inner double-quotes before they reached bash. The fix was discipline: bare commands only, and put anything complex into a real .py file that Python reads directly.
The solution — go native, and go torch-free Windows Subsystem for Linux (WSL2) had working GPU pass-through, the system ptxas assembler, and Python. Installing the real Linux Triton (triton 3.7.1) there gave the exact upstream environment. And because this bug is a pure code-generation bug, it can be reproduced with ahead-of-time compilation only — no GPU launch, no PyTorch, no expensive hardware. Compile the kernel, read the generated code, count instructions.

6. The reproducer: four kernels

The issue author supplied a beautiful minimal reproducer: four nearly-identical kernels that isolate the trigger by changing one thing at a time. All operate on a small 16 × 256 tile of 32-bit floats. s is a per-row scalar (the sum of each row), broadcast back across the row.

KernelWhat it computesPurpose
Ay = x / s, then reducea single division, then a sum — the control
By = x / s; w = y / s, then reducethe chained division — the bug
Cy = x / s; w = y / s, no reducechained division, but nothing consumes it
Dr = 1/s; y = x*r; w = y*r, then reducethe reciprocal work-around

The scientific method in miniature: A vs B isolates "chained division," B vs C isolates "feeds a reduction," and D shows a work-around. Both conditions — a chained division and a following reduction — are required to trigger the blow-up.

python — the essence of the reproducer

# build kernel B, compile ahead-of-time for sm_90, count the divides in the PTX
def compile_div_count(body, cap=90):
    ... # assemble a @triton.jit kernel from `body`
    cc = triton.compile(source, target=GPUTarget("cuda", cap, 32),
                        options={"num_warps": 4})
    return cc.asm["ptx"].count("div.full.f32")   # the hardware FP32 divide

7. Reading the evidence

Beginner note — PTX and div.full.f32 PTX is the assembly-like language a GPU kernel is compiled to; ptxas turns PTX into final machine code. div.full.f32 is the PTX instruction for one full-precision 32-bit float division. Counting how many appear tells us how much redundant work the compiler emitted.

Compiling all four kernels and counting produced a table that makes the bug impossible to miss — and it reproduced faithfully on the latest release (3.7.1), on two different GPU architectures:

KernelPTX linesdiv.full.f32compile time
A — single div → reduce1,777320.1 s
B — chained div → reduce24,0624,128~25 s
C — chained, no reduce1,206640.1 s
D — reciprocal work-around13,6951610 s

Kernel B does barely more arithmetic than A or C, yet emits ~65× more divisions.

Why the reproduction is trustworthy The div.full.f32 counts for A (32) and C (64) matched the original report exactly, which proves the setup is faithful rather than coincidental. And reproducing on the newest release, 3.7.1, made the finding stronger than the original report: the bug is still live.

Part III — Root-cause analysis Advanced

8. How a Triton kernel becomes GPU code

Beginner note — a compiler is a pipeline Your kernel is lowered through a series of intermediate representations (IRs), each closer to the metal. Every arrow is a set of "passes" that rewrite the program. To find a bug you ask: at which arrow did things go wrong?

The single most useful idea in the whole investigation is that each stage's text can be dumped and inspected. If we count divisions at every stage, the stage where the count explodes tells us which arrow — which set of passes — introduced the problem.

9. Bisecting by IR stage: the 2 → 4,128 jump

The MLIR-level division operation is arith.divf on a whole tensor; the PTX-level one is div.full.f32 per element. Counting both across the stages for kernel B:

Stagelinesarith.divfdiv.full.f32
TTIR8620
TTGIR8820
LLVM IR22,44100
PTX24,01804,128
The decisive clue The division count is exactly 2 all the way through TTGIR — the Triton-GPU IR is pristine, just two tensor-level divisions. The explosion to thousands happens only when TTGIR is lowered to LLVM/PTX. So the divisions are fine; the layout the second division is computed in is not.

10. GPU layouts in 5 minutes

Beginner note — threads, warps, and "elements per thread" A GPU groups threads into warps of 32. A tensor spread over the GPU needs a layout: a rule saying which thread holds which element. If a 16×256 tile (4,096 elements) is spread evenly over 128 threads, each thread holds 32 elements — and the compiler emits the math 32 times per thread. If instead the layout makes every thread hold all 4,096 elements, the math is emitted 4,096 times. Same result, 128× the work.

Triton has several layout kinds. Two matter here:

  • #blocked — a healthy, distributed layout: the 256 columns are spread across the 32 lanes of a warp and 4 warps. Each thread holds ~32 elements.
  • #linear — a general layout defined by "basis vectors." When its per-lane and per-warp basis vectors are all zero, it means the data does not move as you change lane or warp — i.e., it is replicated across every lane and warp.

11. The smoking gun: a replicated layout

Dumping the pristine TTGIR for kernel B shows the two divisions living in different layouts, with a layout conversion between them:

TTGIR — trimmed to the essential lines

#blocked = sizePerThread=[1,1], threadsPerWarp=[1,32], warpsPerCTA=[1,4]   // distributed
#linear  = register=[[1,0],[2,0],[4,0],[8,0]], lane=[[0,0]x5], warp=[[0,0]x2]  // lane/warp ALL zero

%y_11 = arith.divf %x_7,  %y_9  : tensor<16x256xf32, #blocked>   // 1st div: distributed  → 32
%y_12 = ttg.convert_layout %y_11 : #blocked -> #linear
%w    = arith.divf %y_12, %y_10 : tensor<16x256xf32, #linear>    // 2nd div: REPLICATED → blows up

Every lane and warp basis of that #linear layout is [0,0]. The 16×256 tensor is replicated across all 32 lanes × 4 warps, so each thread materializes the whole tensor. The arithmetic closes the case:

The numbers that pin the diagnosis Kernel A (one division in #blocked) emits 32. Kernel B emits 4,128 = 32 + 4,096. That is: the first division in #blocked costs 32, and the second division in the replicated #linear costs 4,096 — every one of the 4,096 elements, on every thread. The theory predicts the exact observed number.

This also explains the other kernels: C has no trailing reduction, so nothing forces the #linear layout and w stays distributed. D does its division once on the tiny 16×1 tensor before broadcasting, so only 16 divisions survive.

12. Which pass is guilty?

Knowing the stage (TTGIR → LLVM) is not enough; dozens of passes run there. Turning on Triton's per-pass IR dump and tracking when w first becomes #linear pinned it to a single pass — TritonGPURemoveLayoutConversions. The proof is in its before/after:

At that passLayout of the two divisions
Input (before)both arith.divf in #blocked — healthy
Output (after)the second divf rewritten into replicated #linear
The pass took good code and made it bad The IR entering the pass had both divisions safely in #blocked. The pass itself pushed the second division into the replicated #linear. That is the exact place a fix must live.

Part IV — Fixing bug #1: the Triton bug Advanced

13. The decision point with a "TODO"

The pass has two halves: a forward phase that assigns each operation a layout, and a backward phase that shuffles conversions around to remove them. When an operation could take several layouts, the forward phase must pick one. That tie-breaker is a function literally named for its own shortcoming:

C++ — the original tie-breaker in resolveConflicts()

// Hacky resolve, prefer block encoding.
// TODO: add a proper heuristic.
Attribute encoding = *info.encodings.begin();        // the ARBITRARY first candidate
bool isLoadOrStore = op && isa<LoadOp, StoreOp, ...>(op);
for (Attribute e : info.encodings) {
  if ((isLoadOrStore && isa<BlockedEncodingAttr>(e)) ||
      (!isLoadOrStore && isa<MmaEncodingTrait>(e))) { encoding = e; break; }
}

The comment says "prefer block encoding," but the code only does so for memory operations. For an ordinary arith.divf, neither branch fires and it keeps the arbitrary first candidate — which, by iteration order, happened to be the replicated #linear. That arbitrary choice is the bug.

14. The one-idea fix

The fix, in one sentence When no memory/matmul preference applies, don't pick arbitrarily — pick the candidate layout with the fewest elements per thread (the least-replicated, most-distributed one).

Better still, the codebase already contained the exact tool needed: getUniqueElemsPerThread(encoding, shape) returns how many elements a thread materializes in a given layout. The patch simply uses it as the tie-breaker:

C++ — the added heuristic (abridged)

if (!foundPreferred) {
  if (auto tensorTy = dyn_cast<RankedTensorType>(it.first.getType())) {
    auto shape = tensorTy.getShape();
    unsigned bestElems = getUniqueElemsPerThread(encoding, shape);
    for (Attribute e : info.encodings) {
      unsigned elems = getUniqueElemsPerThread(e, shape);
      if (elems < bestElems) { bestElems = elems; encoding = e; }  // prefer least-replicated
    }
  }
}

For kernel B this compares #blocked (32 elements/thread) against #linear (4,096) and correctly keeps #blocked. The second division stays distributed, and kernel B drops from 4,128 divisions to ~64 — matching kernel C.

15. Why it is correct

Three independent arguments support the fix:

  1. It only changes arbitrary choices. The new code runs solely in the branch that previously took "the first candidate" with no real reason. It cannot regress the deliberate memory/matmul cases.
  2. The arithmetic predicts the outcome. getUniqueElemsPerThread returns 32 for #blocked and 4,096 for #linear, exactly reproducing the observed 32 + 4,096.
  3. A cross-check from the other half of the pass. The backward phase already contains the same elements-per-thread cost guard, so it would never have created this inflation. That the inflation happens anyway means it came from the forward phase — precisely the code we patched.
Confidence, honestly stated These three arguments raised confidence that the fix targets the right function from roughly a coin flip to about 85% — high, for a compiler change that has not yet been compiled. The remaining uncertainty is exactly the kind only a real build can settle.

16. Packaging: branch, patch, test, harness

A fix is only useful if it can be built, verified, and reviewed. The work was packaged as:

  • a git branch fix/10987-elementwise-replicated-layout (commit fa1dca9);
  • a portable 10987-fix.patch, verified to apply cleanly to fresh main;
  • a regression test that asserts kernel B stays under 128 divisions (it was 4,128);
  • a one-command build-and-test harness for a Linux GPU box.

Part V — Fixing bug set #2: bugs in my own work Intermediate

Writing the fix was only half the job. The instruction that followed — "check the gaps and bugs" — turned the same skeptical eye on the deliverables themselves. This is the part most people skip, and it is where a lot of real bugs live.

17. "Check the gaps and bugs"

The single biggest risk was an assumption: that resolveConflicts was even the right place. If the replicated layout were baked in earlier — by the reshape or reduction layout inference — the patch would be a no-op. That question had to be answered before spending money renting a GPU to build.

18. The check that de-risked everything

Rather than guess, the installed Triton's per-pass IR dump was used to watch exactly when w becomes #linear. It became #linear on the output of TritonGPURemoveLayoutConversions — the patched pass — with clean #blocked input. Combined with the backward-phase cross-check, this confirmed the patch is in the right pass without compiling anything.

19. Four bugs found and fixed

#Bug in the deliverablesFix applied
1 The build script never installed a C++ compiler or Python headers — a fresh rented box would fail to build Triton at all. Added a conditional apt-get install build-essential python3-dev.
2 No baseline: the test could pass vacuously if main behaved differently from the analyzed 3.7.1. Rewrote the procedure to build main first, confirm the bug (B ≈ 4,128), then apply the patch and confirm the fix.
3 The unit test was left as "write it yourself later" — a real gap for a pull request. Wrote a proper MLIR lit test from the real captured pre-pass IR and committed it to the branch.
4 The C++ named a type (ArrayRef<int64_t>) that carried a small namespace risk. Changed it to auto — same behavior, zero risk.

20. Honest residual risks

What a build still needs to confirm
  • ~15% chance the fix is the right pass but the wrong function within it (forward vs. backward phase). Ordered fallbacks are documented.
  • The analysis was on 3.7.1; the patch targets main. The baseline-first procedure is the guard against drift.
  • The lit test's exact syntax may need a small tweak on main.
  • The heuristic touches a central pass; the existing test suite is the regression guard.

Stating these plainly is not weakness — it is what separates an honest engineering hand-off from an over-sold one. Every risk has a documented check or fallback.

Part VI — Shipping & why it matters

21. Build & verify on a rented GPU

The whole package is designed so the first run on a rented GPU box (an RTX 4090) is decisive. The procedure builds unpatched main first to prove the bug is present, then applies the one-file patch and rebuilds incrementally (minutes, not the full 30–40), then runs the regression test.

bash — the decisive before/after

python3 test_10987_div_blowup.py   # baseline (main):  B ~4128  → FAIL, bug present
git apply 10987-fix.patch
python3 -m pip install -e .        # incremental rebuild (1 file changed)
python3 test_10987_div_blowup.py   # patched:         B  <128  → PASS

22. Submitting the pull request

With the test green, the branch is pushed to a fork and a pull request is opened against triton-lang/triton:main, referencing Fixes #10987 and carrying the root-cause write-up and the numbers. A merged compiler fix here is worth more, as a hiring signal, than any number of résumé edits.

23. Full circle

Back to the original question The project began with "what are my chances at OpenAI?" and ends with a concrete, verified, ready-to-submit fix to OpenAI's own compiler — the exact kind of public, verifiable, elite-domain work that the honest assessment identified as the one thing capable of moving the needle. The bottleneck was never "more experience." It was "undeniable proof." This is that proof, built end to end.

How the bugs were fixed — the short version

There were two kinds of bug in this project, and both were fixed the same disciplined way: reproduce → bisect to the exact mechanism → change the smallest correct thing → prove it.

  • The Triton bug (#10987) was fixed by tracing a 65× code blow-up to a single arbitrary layout choice in one compiler pass, and replacing that arbitrary choice with a principled one (prefer the least-replicated layout), backed by the code's own existing cost function.
  • The bugs in my own deliverables were fixed by refusing to trust the fix — verifying the target pass with an IR dump, hardening the build script, adding a real baseline and a real test, and writing down every remaining risk with its check.

Appendix A — The patch

The complete change to lib/Dialect/TritonGPU/Transforms/RemoveLayoutConversions.cpp, in LayoutPropagation::resolveConflicts(). It leaves the existing memory/matmul preferences untouched and only replaces the previously-arbitrary tie-break.

C++ — the added block, with its explanatory comment

bool foundPreferred = false;
for (Attribute e : info.encodings) {
  if ((isLoadOrStore && isa<BlockedEncodingAttr>(e)) ||
      (!isLoadOrStore && isa<MmaEncodingTrait>(e))) {
    encoding = e; foundPreferred = true; break;
  }
}
// issue #10987: when no memory/MMA preference applies, the choice above is
// just the arbitrary first candidate. That can be a replicated layout (e.g.
// a linear layout whose lane/warp bases are all zero), in which every
// thread materializes the full tensor. Lowering an elementwise op in such a
// layout emits it once per redundant copy (a chained `x / s / s` feeding a
// reduce blew up from ~64 to 4128 `div.full.f32`). Break the tie toward the
// least-replicated candidate: the one with the fewest elements per thread.
if (!foundPreferred) {
  if (auto tensorTy = dyn_cast<RankedTensorType>(it.first.getType())) {
    auto shape = tensorTy.getShape();
    unsigned bestElems = getUniqueElemsPerThread(encoding, shape);
    for (Attribute e : info.encodings) {
      unsigned elems = getUniqueElemsPerThread(e, shape);
      if (elems < bestElems) { bestElems = elems; encoding = e; }
    }
  }
}
